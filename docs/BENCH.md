## 4. 詳細結果

### 4.1 圧縮 / 解凍（K1/K2/K3）

**A. C コア直呼び**（`zipnn_core.zipnn_core` / `combine_dtype`、Gaussian σ=0.02 の合成テンソルバイト、2 スレッド。全ケースで往復 SHA‑256 一致）:

| dtype   | サイズ | 圧縮比 | 圧縮 MB/s | 解凍 MB/s | 圧縮ピーク | 解凍ピーク |
| ------- | ------ | ------ | --------- | --------- | ---------- | ---------- |
| bf16    | 32 MB  | 0.6623 | 800.7     | 899.5     | 92 MiB     | 103 MiB    |
| bf16    | 96 MB  | 0.6623 | 454.4     | 1,049.8   | 233 MiB    | 273 MiB    |
| bf16    | 192 MB | 0.6623 | 395.5     | 1,004.5   | 466 MiB    | 528 MiB    |
| f32     | 32 MB  | 0.8313 | 542.2     | 1,722.0   | 103 MiB    | 108 MiB    |
| f32     | 96 MB  | 0.8313 | 337.4     | 1,182.4   | 274 MiB    | 289 MiB    |
| f32     | 192 MB | 0.8313 | 361.8     | 1,049.8   | 531 MiB    | 561 MiB    |
| f16     | 32 MB  | 0.8434 | 612.8     | 1,381.7   | 103 MiB    | 108 MiB    |
| f16     | 96 MB  | 0.8434 | 462.0     | 1,359.7   | 275 MiB    | 290 MiB    |
| f16     | 192 MB | 0.8434 | 411.0     | 1,025.4   | 534 MiB    | 563 MiB    |
| fp8e4m3 | 32 MB  | 0.6697 | 410.4     | 1,057.4   | 92 MiB     | 103 MiB    |
| fp8e4m3 | 96 MB  | 0.6697 | 346.1     | 693.2     | 242 MiB    | 274 MiB    |
| fp8e4m3 | 192 MB | 0.6697 | 372.9     | 666.5     | 472 MiB    | 530 MiB    |

ピーク RSS の内訳は「Python 基底 ~36 MiB + 入力 + 平面バッファ + 出力」で、
**限界倍率（(peak − 基底) / 入力）は bf16 で 1.75× → 2.05× → 2.24×（32/96/192 MB）、
f32 で 2.57×（192 MB）**とサイズとともに漸増（チャンク表・アロケーションスラック）。
12 GB への線形外挿で **約 27–31 GB**（K1 の Plan 見込み「24 GB 超」を裏書きし、やや悪い）。

**B. Neo 端到端**（`py/compress.py` の実関数。torch 基底 RSS 241 MiB を差し引いた限界値で評価。解凍後は原本と SHA‑256 照合し **byte‑exact 一致**を確認）:

| モデル                          | 圧縮       | 解凍       | 圧縮比 | 圧縮ピーク（限界）     | 解凍ピーク（限界） |
| ------------------------------- | ---------- | ---------- | ------ | ---------------------- | ------------------ |
| 合成 bf16 64 MB（16 テンソル）  | 171.9 MB/s | 288.7 MB/s | 0.6623 | 409 MiB（+168 = 2.6×） | 352 MiB（+111）    |
| **実モデル** MiniLM f32 86.7 MB | 141.5 MB/s | 206.6 MB/s | 0.8192 | 456 MiB（+215 = 2.5×） | 404 MiB（+163）    |

C コア単体（395–800 MB/s）に対する e2e の律速（141–172 MB/s）は、テンソルごとの
Python ループ・`tensor.clone()`（C コアの入力破壊対策）・RAM dict 蓄積・`save_file`
書き戻しであり、Plan §4.3 のゼロコピー設計が回収する対象そのものである。
実モデル f32 の圧縮比 0.8192 は README の「realistic checkpoints 60–80 %」の f32 側と整合。

### 4.2 デルタ圧縮（K4）

32 MB f32 ペア（全要素に小さなドリフト = フルファインチューン相当。`delta_compress_files` →
`delta_decompress_file` → 復元 SHA‑256 **byte‑exact 一致**）:

| フェーズ | 時間    | ピーク RSS          | 限界倍率（ft 比）   |
| -------- | ------- | ------------------- | ------------------- |
| 圧縮     | 0.349 s | 414 MiB（基底 241） | **+173 MiB = 5.4×** |
| 解凍     | 0.214 s | 424 MiB（基底 241） | **+183 MiB = 5.7×** |

デルタサイズ比 0.6891（このフィクスチャはバイトの ~6 % が差分。実 FT では一般にさらに小さい）。
両ファイル全文の `f.read()` + パディングコピー + numpy XOR コピー + C コア平面、という
Plan §1.2.2 #5 の内訳通りで、**実測倍率は「4–5 倍」の見込みをやや上回る**。
12 GB ペア換算で 65 GB 級 = Plan の「50 GB 級」見積りと同オーダー。

### 4.3 既知欠陥の再現（K5 — Plan 付録 C）

| ケース                                                                                                                   | 結果                                           |
| ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------- |
| 生 C コア: `zipnn_core(header, bytearray(262144+k), 4, 1, 220, …)`、k ∈ {1,2,3}                                          | **3/3 SIGSEGV（exit −11）100 % 再現**          |
| **生産経路**: `py/compress.py delta_compress_files()` に、パディング後総長 % 256 KiB = 1 の手組み safetensors ペアを投入 | **SIGSEGV（Python 例外化されずプロセス死亡）** |

2 番目は付録 C.5 の「デルタ圧縮は危険（到達可能）」を **Neo の実ルート経由で実証**した
もの（ヘッダー長を解析的に調整した手組みペアで総長を制御。safetensors 公式
シリアライザはヘッダーを 8 バイト境界に整列するため、奇数剰余は任意ヘッダー長を
持てる実ファイル — 別ツール出力や手編集 — で生じる）。Rust 版では同ケースを
回帰テストに固定する（Phase 3 の完了条件）。

**付録 C.3 の全ケース行列**（22 ケース: dtype32 クラッシュ 8 ＝ 1st/2nd チャンク境界
×{1,2,3} ＋低エントロピー、対照 9 ＝チャンク境界ちょうど・%4≥4 最終チャンク・64/67 B、
dtype16 経路 5 ＝境界・奇数長）は `scripts/bench/bench_c_defects.py` で一括再実行でき、
証跡を [`scripts/bench/results/c_defects.json`](../scripts/bench/results/c_defects.json)
にコミットしている（2026‑09‑23 実行: **SEGFAULT 8/8・対照往復一致 14/14・逸脱 0** ＝
`appendixCReproduced: true`。別サンドボックスでの独立実行でも同一結果）。

### 4.4 スキャン（K9/K10）

5,000 モデル合成ライブラリ（7,532 ファイル、md サイドカー 1,028・プレビュー 1,503）で
`ModelManager.scan_models()` 全面走査（6 タイプ合計 5,016 エントリ）:

| 計測                     | 時間          | 備考                                                       |
| ------------------------ | ------------- | ---------------------------------------------------------- |
| 冷間（初回、3 回中央値） | **1.332 s**   | `drop_caches` 不可（コンテナ）のため dentry キャッシュは暖 |
| 暖間（同プロセス再走査） | **0.501 s**   | `_SITE_CACHE` ホット。**差分経路はなく毎回全面走査**       |
| `scan_hygiene`           | 0.235–0.250 s | 孤立サイドカー 1・空フォルダ 1 を正しく検出                |

本環境（高速ローカルストレージ・2 vCPU）では K9 目標（≤2 s）内に既に入っているが、
Plan の見込み（5–20 s）はネットワークストレージや HDD を含む実環境の話であり、
`_model_site_info_of` の 4 KB 先頭読みがネットワーク越しに 1,028 回走る構成では
容易にその域に入る（コード上の根拠: manager.py の `_SITE_CACHE` 注释）。
K10（暖間 ≤100 ms）は現行構造では原理的に未達（全面再走査 0.5 s）で、
Phase 5 の永続インデックス + 差分スキャンが必要条件。

### 4.5 ヘッダー解析（K11/K12）

8.42 MB MoE ヘッダー（64,491 テンソル、DeepSeek 風命名）で `py/utils.py` の実関数:

| ステップ                       | 中央値     | 備考                                                |
| ------------------------------ | ---------- | --------------------------------------------------- |
| ヘッダー読み取り（8 B + 本体） | 5.4 ms     | `comfy.utils.safetensors_header` 相当               |
| `json.loads`                   | 506 ms     | 64k dict の materialize = コストの主体              |
| テンソルリスト構築             | 89.5 ms    | `get_model_tensors` のループ                        |
| **`get_model_tensors` 合計**   | **930 ms** | 反復間 453–1,091 ms（1 GiB 環境の GC 負荷でブレ大） |

- Plan 見込み（200–400 ms）を **2 倍以上**上回る。K11 目標 ≤40 ms に対し、
  現行 Python 経路は 23 倍の距離。§2 の jiter 実測（10.6 ms）は Rust 化で
  目標が十分達成できることを示す。
- **副次発見**: `get_model_metadata()` の 1 MiB ガードにより、ヘッダーが 1 MiB を
  超える MoE モデルでは `__metadata__`（ZipNN 圧縮記録を含む）が**黙って空扱い**になる。
  8 MB ヘッダーで実測確認（`metadataEmptyDueToGuard: true`）。Phase 5 の B4
  （ヘッダー解析内製化）で 32 MiB ガードへ統一すべき候補。
- K12: Quick Win A1 適用前、この 0.93 s はモデル詳細を開くたびに
  **イベントループ全体（WebSocket 配信含む）を停止**させていた。A1 により
  ルートは executor 経由になり阻塞は解消（Quick Win A1、commit 047568b）。

| `identify.compute_hashes`（5 算法 1 パス）  | 0.920 s | **278 MB/s** | SHA256+AutoV2+AutoV1+CRC32+BLAKE3。値の相互一致を確認 |

10 GB 換算: 5 種 1 パス ≈ **38 s**（K8 目標 ≤15 s は Rust 並列 + SHA‑NI 前提。
本 CPU は SHA 拡張なしで AVX2 経路）、ダウンロード後検証の再読込 ≈ **+31 s**
（K7 目標「ゼロ」= インライン化で丸ごと消去）。SHA256 値は 3 経路で完全一致
（`compute_hashes` の正しさの相互検証にもなっている）。

## 6. 観察と結論（Phase 1 以降への申し送り）

1. **付録 C の欠陥はこの環境でも 100 % 再現**し、さらに **Neo の生産デルタ経路で
   到達可能**であることを実証した（§4.3）。K5 の重大度評価は実測で裏付けられた。
2. **ヘッダー解析は Plan 見込みより深刻**（930 ms vs 200–400 ms）。K11/K12 の
   優先度は計画通りで正しかった。加えて `get_model_metadata` の 1 MiB ガードが
   大型 MoE でメタデータを黙って落とす挙動を発見（§4.5、Phase 5 B4 の設計入力）。
3. **json.loads が支配的コスト**（506/930 ms）。jiter はその 48 倍速で、
   選定は計測により確定した（§2）。
4. **e2e の律速は Python/torch 層**（C コア比 2.3–2.8 倍遅い）。Rust 化の速度目標
   （K2 ≥1.5 倍 / K3 ≥2 倍）は **e2e 値を基点**に判定する。
5. **ピーク RAM 倍率の実測は Plan 見積りよりやや悪い**（圧縮 2.2–2.6×、デルタ 5.4–5.7×）。
   K1/K4 の「<1 GB」目標の価値はむしろ大きい。
6. **K9 は環境依存が極めて大きい**（本環境の冷間 1.33 s vs Plan 見込み 5–20 s）。
   Phase 5 の完了判定は「参照機 + ネットワークストレージ」構成での再計測を必須とする。
7. `ensure_zipnn` の初回 1.69 s はほぼ torch import。Rust コア（6 ms）への移行は
   K13 を桁で改善する（§4.7）。
8. 本環境（1 GiB RAM）では 12 GB 級の直接計測は不可能なため、K1/K4 の 12 GB 換算は
   **32–192 MB 実測の線形外挿**である（倍率の線形性は 3 点で確認済み）。
   参照機での裏取りは Phase 2 の L4 テストと併せて行う。

### 6.2 速度（32 MB Gaussian フィクスチャ、threads=2、steal ゲート付きクリーン窓）

計測プロトコル: 両側とも in-process・warm、/proc/stat のホスト steal が
窓容量の ~5 % を超えるサンプルは棄却（同一ルールを C 側 Python ループと
Rust 側 `znn-cli bench` に実装）、交互ブロック × 複数回、側ごとの最小値
（=干渉ゼロ窓のスループット上限）を比較。**この共有 2 vCPU 機ではこれ以外
に再現性のある比較が成立しない**（未ゲート計測は同一設定で 2–3 倍揺れる。
C 側すら Phase 0 記録値と同日クリーン窓で最大 2.4 倍乖離 — f32 解凍
1,722→718 MB/s、f16 圧縮 613→1,020 MB/s — したため、Phase 0 記録値との
比較は機械状態が違い無効。同一セッション比較のみが意味を持つ）。

**最終結果（virtual-raw 平面最適化後、コミット済み speed.json）— 8 指標
すべてで C を超過**:

| dtype | 圧縮 C→Rust (MB/s) | 倍率  | 解凍 C→Rust (MB/s) | 倍率  |
| ----- | ------------------ | ----- | ------------------ | ----- |
| f32   | 531 → 580          | ×1.09 | 748 → 1,355        | ×1.81 |
| bf16  | 531 → 683          | ×1.29 | 664 → 993          | ×1.49 |
| f16   | 512 → 741          | ×1.45 | 710 → 1,130        | ×1.59 |
| fp8   | 511 → 714          | ×1.40 | 570 → 730          | ×1.28 |

- 同一プロトコルの連続 2 実行（最適化中間版 ×1.18–1.37、最終版
  ×1.09–1.45）とも **8/8 が ×1.0 以上**。圧縮率差は全 dtype Δ0.0000 %。
- 正直な変動注記: この共有機の「最も静かな窓」では C の bf16/f16 圧縮が
  ~950–1,030 MB/s に達することがある（Phase 0 記録 337–800 の上限も超過。
  C は 32MB バイト毎 clone + pthread spawn を計測窓内で支払うためメモリ
  帯域競合への感度が Rust 側より高く、窓の質で ~2 倍振れる。Rust 側は
  580–790 で安定）。virtual-raw 導入後の Rust 上限は静穏窓で C 上限に
  接近すると推定されるが、両者の最静穏窓が同時に来る機会が得られず
  未観測。**ゲートは「同一セッション・同一 steal ゲート・側別最小値」
  プロトコルで判定**し、連続 2 実行で全指標通過。
- Phase 1 で実施した最適化の記録: 4-way ヒストグラム（C HIST_count_parallel
  移植）、packed CTable、register-local ライタ（5 シンボル/フラッシュ —
  フラッシュ周期不変性を証明の上でバイト同一を維持）、16B ブロック
  インターリーブ（split2 968→2,055 MB/s、join2 → 14,192 MB/s L2 暖時。
  32B 化は逆効果で却下）、X2 デコードの 8B ウィンドウ + 4 ストリーム
  インターリーブ + 固定長 [DeltX2;4096] 表（C の ILP 構造再現）、
  nb=1 ゼロコピー経路、並列アセンブリ、スレッドローカルスクラッチ全般、
  そして **virtual-raw 平面**（raw 確定の平面をマテリアライズせず
  アセンブリ時に `extract_plane` で src から出力へ直接展開 — clone と
  refill memset を全廃し bf16/f16 圧縮 ×0.72–0.78 → ×1.18–1.45 に反転。
  バイト同一は 10,500 ケースで再証明）。
- **unsafe は不使用**（ユーザ指示 2026‑09‑23 + Plan §3.4.2）。
  `#![deny(unsafe_code)]` はクレート全体で維持。

### 6.3 圧縮率の保証（ユーザ要件 2026‑09‑23: 「せめて 67 % は下回らない」）

Neo の圧縮出力は C と**バイト同一**（L2 フル 10,500 ケースで 100 % 一致）
であるため、圧縮率は**あらゆる入力で C 版と恒等的に一致する** — 要件は
構造的に保証される。実測（Gaussian フィクスチャ、Phase 0 の C 記録 §4.1 と
同値）: **bf16 = 0.6623（≒66 %、実モデルで観測される ~67 % と同水準）**、
fp8 = 0.670、f32 = 0.831、f16 = 0.843。dtype 別の差は平面化の効果差であり
C と完全に同一の挙動（将来の Neo 拡張帯 dtype は Phase 4 で別途設計するが、互換帯の比率は C と永遠に同一）。

### 6.4 上流メモリバグの Neo 内修正（ユーザ指示 2026‑09‑23）

上流 zipnn への issue 起票は行わず（PAT スコープ外 + 起票しない判断）、
**付録 C のメモリバグ群は Neo 実装内で完全修正済み**であることを証跡で担保:

- 設計: 全経路 bounds-checked・unsafe ゼロ・敵対的入力は Err（OOB 不可能）。
- 回帰: 付録 C の全クラッシュ長（4 平面 final-chunk 1–3B 系）を L1 単体 +
  L2 フル（495/495 正常処理・クラッシュ 0）+ L3 ファズ（ASan 付き ~60 万
  実行パニック 0）で固定化。
- ファズ検出のオーバーフロー 2 件（cumSizes 平面オフセット / orig_len 加算）
  も修正済みで、クラッシュ入力はコーパスに回帰シードとしてコミット。
- Phase 3 のデルタ経路（C では SEGFAULT 到達を実証済み）はこの codec を
  使うため、Neo では同バグが構造的に発生しない（Phase 3 で実証する）。

### 6.5 L3 ファジング（Phase 1 スモーク）

### 7.1 スループットとピークメモリ（実測、この 2 vCPU / SHA‑NI なし機）

**K2/K3 がこのマシンで目標未達の理由（内訳を実測で特定 — 推測ではない）**:

1. **sha2 の soft バックエンドが壁**。この CPU（Skylake‑SP）は SHA 拡張を
   持たず、sha2 0.11 の SHA‑256 には **AVX2 バックエンドが存在しない**
   （一次ソース: sha2 0.11 README「Backends」— `x86-avx2` は SHA‑512 専用、
   SHA‑256 は `x86-sha`(SHA‑NI) か `soft` のみ）→ 実測 **~156 MB/s**。
   分離計測: 検証 OFF の解凍 = **352 MB/s**（0.182 s）に対し検証 ON =
   77.2 MB/s（0.549 s）— **壁時間の ~85 % が K6 検証ハッシュ**。圧縮側は
   sha を専用スレッドで並行化済みだが、2 vCPU に空きコアがなく壁 ≈ sha 律速。
2. 比較対象の legacy には検証も fsync も**存在しない**（K6=「なし」が
   Phase 0 の記録通り）。機能差込みの比較である点を明記する。
3. fsync はこの volatile overlay で ~5 ms と無視できる（実測）。

**パイプライン単体の実力**（検証ハッシュを除いた同一セッション実測/算出）:
解凍 352 MB/s = legacy 比 **×1.18**（このストレージ上限 ~627 MB/s に逼近）。
圧縮は sha 並行窓を差し引いて ≈0.15–0.20 s → **320–430 MB/s = ×1.5–2.0**
（codec 単体は L2 実測 bf16 圧縮 683 MB/s・解凍 993 MB/s が上限）。

### 7.3 実装上の決定記録（Plan からの逸脱を含む — すべて実測/一次ソース根拠）

1. **単一書き込みパス（H_max ヘッダー予約）**: Plan §4.3 の「RAM/spoil →
   逐次書込」に対し、予約ヘッダー領域（JSON 末尾スペース = 正当な JSON 空白 —
   レガシーのデルタ パディングと同じ技法）へ seek‑back で確定ヘッダーを
   パッチする方式を採用。スポイル方式（3 倍 I/O）はこのストレージで
   K2 を確実に割る実測（見積 +2 pass ≈ +0.4 s/64MB）ため。領域長は
   ソースヘッダーからエントリごとに厳密上限（桁数上限）を構成するので
   超過は原理的に起きず、防御的フォールバック（再書き込み）も実装・
   テスト済み（`hmax_slack<0` で強制発動）。
2. **`znn_neo_exact` フラグの新設**（Plan §4.4.3/§4.7.4 の調整点): 原本
   ヘッダーが正準形でないファイル（手編集・特殊ライタ）では byte‑exact
   復元が原理的に不可能なため、圧縮時に正準性を判定して記録。解凍時の
   sha 不一致は exact=1 でのみ「破損扱い（.corrupt 退避 + エラー）」、
   exact=0 では Plan §4.7.4 の最低保証（構造検証: テンソルデータ +
   メタデータ等価）へダウングレードする。§4.4.3 の文言（不一致 → 一律
   エラー）をそのまま実装すると非正準原本のファイルが**永久に解凍不能**
   になるため、計画書の二つの節の意図を両立させる解釈として実装した。
3. **`znn_neo_src_meta_absent` キーの新設**: 原本に `__metadata__` が
   「無い」ことと「空マップで在る」ことの区別（参照 Writer は None を
   キー省略、空マップを `{}` として書く — バイトが違う）。これが無いと
   byte‑exact 復元が成立しない。レガシー解凍側もこのキーを尊重するよう
   更新済み（クロスパスで復元バイトが一致する）。
4. **メタデータ順序の保持**: 参照実装（safetensors 0.8.0 Rust、一次ソース
   精読 2026‑09‑24）は `__metadata__` を **HashMap でシリアライズするため
   キー順がプロセスごとにランダム** — 複数キーのメタデータではレガシー
   往復の byte‑exact が偶然に依存していた。Neo の Writer は原本の JSON 順
   を保持するため、多キー メタデータでも決定的に byte‑exact（潜伏バグの
   修正に相当 — テスト `test_compressed_metadata_matches_the_legacy_contract`
   ほかで固定）。
5. **fp8 チャンククランプの潜在バグ修正**（Phase 1 監査で発見):
   `codec::decompress_container` が zipnn.py の「num_buf==1 のとき
   chunk=min(128KiB, 2^byte14)」を適用しておらず、生産 fp8 ブロックを
   全て誤パースする状態だった（Phase 1 では呼び出し元が存在せず未顕在化 —
   L2 はチャンクを明示引数で渡すため通らない）。修正 + 回帰テスト
   `fp8_container_chunk_clamp`。同監査で Plan §7 R10 の「バージョンバイト
   厳密検査」も実装（0.5.0–0.5.4 のみ受理、将来バージョンは明示エラー）。
6. **ジョブ完了の権威シグナルは outcome レコード**（実測で発見した競合):
   パイプラインの phase=Done 設定とスレッドの outcome 記録の間にごく短い
   窓があり、phase だけを見ると `job_result` が「未完了」を返す
   （bench ハーネスが実測で検出）。`job_progress` は outcome の存在を
   唯一の終端条件とし、窓の間は `verify` を報告する（本番ポーリング
   ループも同じ API を使うため競合は構造的に消滅）。
7. **paranoid の内部検証デコードはジョブ進捗を駆動しない**（done>total に
   なる 200 % 表示バグを実測で発見 → 内部 Hooks は progress=None、
   cancel のみ共有）。

### 8.1 K4 — ピークメモリ（限界倍率 = (peak − 基底) / ft サイズ）

| 指標                      | native（Rust ストリーミング）              | legacy（torch+C）                           | 比                  |
| ------------------------- | ------------------------------------------ | ------------------------------------------- | ------------------- |
| 圧縮限界 RSS              | **+66.8 MiB = 2.09×**                      | +173.6 MiB = **5.43×**（Phase 0 記録 5.4×） | **÷2.6**            |
| 解凍限界 RSS              | **+54.2 MiB = 1.69×**                      | +183.1 MiB = 5.72×（Phase 0 記録 5.7×）     | ÷3.4                |
| 壁時間（圧縮）            | 0.304 s（**ftSha256 インライン算出込み**） | 0.295 s（検証なし）                         | 同等（機能差込み）  |
| 壁時間（解凍）            | 0.285 s（**インライン sha 検証込み**）     | 0.197 s（検証なし）                         | +0.09 s = sha 律速  |
| 復元 byte‑exact（sha256） | **True 3/3 ラウンド（verified=sha256）**   | True（検証なしの偶然一致）                  | **K6 のデルタ側 ✓** |

**限界値の内訳（正直な記録）**: native の限界 +66.8 MiB のほぼ全ては
**mmap の clean ファイルページ**（base 32 MB + ft 32 MB = 64 MB — 回収可能
ページであり、メモリ圧迫下ではカーネルが.evict する）。匿名ワーキング
セットは O(1 MiB ストリーミングチャンク + codec スクラッチ) ≈ 数 MB で
**ファイルサイズに依存しない**（裏付け: 8.2 の 0.5 MiB 級ペアでは限界
+3–4 MiB、32 MB ペアで +67 MiB ≈ 両ファイルの合計に比例 = ページキャッシュ
由来の証左）。legacy の 5.4× は**匿名コピー**（両ファイル全文 + パディング
コピー + numpy XOR 出力 + C 平面バッファ — 回収不能）である。よって
12 GB ペア換算: legacy ≈ 65 GB 級（実機 OOM/スワップ）に対し native は
匿名 < 10 MB + 回収可能ページのみ → **K4「< 1 GB」達成（構造 + 実測）**
— §7.1 K1 と同じ「サイズ非依存設計」の論証。

壁時間の注記: native 圧縮は検証なし legacy と同タイムで、ftSha256 の
インライン算出（この SHA‑NI なし機では ~156 MB/s = 32 MB で ~0.2 s、
§7.1）を**追加機能として**含む。解凍差 +0.09 s も同じ sha 律速で、
SHA‑NI + NVMe の参照機ではデコード/XOR の裏に隠れる（§7.1 K3 と同型の
外挿。K2/K3 と違いデルタには Phase 0 側の「≥1.5×/≥2×」目標が無い —
デルタの KPI は K4/K5 のみ）。

### 10.2 K7 / K8 — ハッシュ（128 MB ターゲット）

| 経路                      | legacy              | native                  | 備考                                                                  |
| ------------------------- | ------------------- | ----------------------- | --------------------------------------------------------------------- |

### 11.1 K15 — 検索 keystroke → 描画（5,050 モデル）

グリッド行パイプライン（filter → sort → chunk）の **JS 作業時間**。
K15 の「keystroke → 描画 ≤ 16 ms」は 1 フレーム予算なので、比較対象は
この JS 作業 + DOM 反映であり、意図的な 150 ms デバウンス（既存の
Optimization B‑3）は含まない。ブラウザ側の paint 脚は
`src/utils/perf.ts` の `mm.grid.queryToPaint`（`__mmNeoPerf.summary()`）として
実 UI で計測できる（ヘッドレスでは再現不能なため分離して記録する）。

| 経路                                                            | p50            | p95                | min            | naive 比（p95） |
| --------------------------------------------------------------- | -------------- | ------------------ | -------------- | --------------- |
| **naive**（Phase 6 以前: トークン正規表現をモデル毎に再構築）   | 6.58 ms        | **10.57 ms**       | 3.97 ms        | ×1.0            |
| C1 のみ（トークン 1 回コンパイル + インライン `localeCompare`） | 1.27 ms        | **3.49 ms**        | 0.63 ms        | **×3.0**        |
| **出荷経路**（C1 + 共有 comparator `compareText`）              | 1.29 ms        | **3.96 ms**        | 0.63 ms        | **×2.7**        |
| 初回グリッド（クエリ無し）naive → 出荷経路                      | 5.36 → 4.95 ms | 7.95 → **7.03 ms** | 4.74 → 4.43 ms | ×1.1            |

- **K15 判定**: keystroke の JS 作業 **p95 3.96 ms ≤ 16 ms**（予算の 25 %）。
  初回グリッドの行構築 **p95 7.03 ms ≤ 1 s**（残りはネットワーク + DOM で、
  5,000 モデルの scan 自体は Phase 5 の K9 = 0.145 s）。

  定義しているのはこのためで、本節の数値は**コミットされた証跡 JSON
  （4 回目実行）と一致**させてある。CI ランナー（Node 22 / 4 vCPU）では

### 11.2 C2 — 照合キー化は**計測により設計を修正した**

5,050 名ソート（`SEGMENTS` コーパスはテンソルツリーの segment 形）と
3,600 名の numeric 形コーパスで、4 通りの comparator を同一実行内で比較した:

| comparator                                                            | p50           | 備考                                                                     |
| --------------------------------------------------------------------- | ------------- | ------------------------------------------------------------------------ |
| `a.localeCompare(b)`                                                  | **1.47 ms**   | V8 は既定 options に**内部キャッシュ済み既定 collator の高速経路**を持つ |
| hoisted `new Intl.Collator().compare`（bind 済み関数を 1 回だけ取得） | 5.13 ms       | 公開 API 経由は **×3.5 遅い**                                            |
| `a.localeCompare(b, undefined, { numeric: true })`                    | **291.23 ms** | options を渡すと高速経路が無効 = **呼び出し毎に collator 構築**          |
| hoisted numeric `Intl.Collator().compare`                             | **9.30 ms**   | **×31.3 速い**                                                           |

→ **Plan §4.8‑C2 の前提（「`localeCompare` ×4 → 共有 Collator で高速化」）は
既定 variant では逆**だった。したがって実装は:

- 既定 variant（グリッドの名前ソート・フォルダソート・ZipNN dtype 集計）=
  `compareText` = **`a.localeCompare(b)` を維持**（最速・意味論不変）、
- numeric variant（テンソルツリーの `naturalCompare` フォールバック脚）=
  `compareTextNumeric` = **hoisted numeric Collator**（×22–32）、
- **両方の**選択は bench ゲート `c2DefaultComparatorIsTheFastestMeasured` /
  `c2NumericHoistingIsFaster` で**機械固定**（将来 V8 の挙動が変われば CI が
  知らせる）。旧直呼び 7 箇所は全て `utils/modelFilter` 経由に集約した。

### 11.3.1 詳細ダイアログ端到端 — fold 以外に 2 つの隠れたコスト（精査で発見・修正）

| 処理                                                                            | 実測                | 状態                                                                         |
| ------------------------------------------------------------------------------- | ------------------- | ---------------------------------------------------------------------------- |
| `ModelContent.vue` の `cloneDeep(props.model)`（テンソル 65,268 オブジェクト）  | **218.5 ms**        | Phase 6 で**参照共有化**（読み取り専用・保存時も送信されないため）           |
| 同じ clone が payload（87,195 ノード）に対しても発生                            | **130.0 ms**        | 同上（Phase 6 で tree を追加していなければ顕在化しなかった cost）            |
| 参考: payload の JSON 往復                                                      | 105.0 ms            | —                                                                            |
| `editorState()` の dirty 判定 = フォーム全体の `JSON.stringify`（テンソル込み） | 数十 ms/回          | 表示用 payload を snapshot から除外（open / reset / 判定のたびに走っていた） |
| Vue の deep `ref` 経由で 65k エントリを走査する Proxy トラップ                  | fold 本体より大きい | `ModelInformation.vue` は `toRaw()` 経由で読むよう修正                       |

つまり **Rust 事前グループ化だけでは端到端の改善は相殺される**（clone 348 ms +
snapshot + Proxy が fold の削減分以上に残る）。3 点を直した後の詳細ダイアログ
（Information タブ）のおおよその内訳は:

|                                  | Phase 6 以前              | Phase 6（fold のみ Rust 化）      | Phase 6（clone/snapshot/toRaw 込み） |
| -------------------------------- | ------------------------- | --------------------------------- | ------------------------------------ |
| テンソル由来のメインスレッド作業 | ≈218 + ≈80 + **1,329** ms | ≈218 + 130 + ≈80 + 60 + **13** ms | ≈**13** ms                           |
| 比                               | ×1.0                      | ×3.1                              | **×120**                             |

（`src/utils/perf.ts` の `mm.info.tensorTree.decode` / `.fallbackFold` /
`mm.info.tensorRows` が実機側の内訳を、`__mmNeoPerf.summary()` で報告する。）

### 11.4 A3（requests → aiohttp）と watch_roots の検証

A3 と watch_roots は**性能ではなく挙動 parity / degrade** が完了条件のため、
数値ゲートは持たない。代わりに:

- **A3**: `tests/test_phase6_http.py` **17 件**が**ローカル aiohttp モックサーバ**
  against で旧 `requests` 経路の可観測契約を固定 —
  `raise_for_status` の逐語文言（`403 Client Error: … for url: …` /
  `503 Server Error: …`）と `.response.status_code`（Civitai 401 誘導文が依存）、
  content-type を検査しない JSON デコード、`(connect, sock_read)` タイムアウト
  写像（`total` 無しの実証 = 120 ms 間隔の 2 チャンクを 1 s read timeout で完走）、
  プロバイダ 3 者の部分結果契約（成功 / 例外 / ハング → `search timed out`）、
  アバターの users→organizations フォールバック + キャッシュ（往復回数まで固定）、
  by-hash の逐次プローブ順と非 200 / 非 JSON スキップ、capped ストリーミング、
  HF recursive tree のサイズ解決と tree 障害時の degrade。
  **スレッドホップは 0**（identify の io worker 内からの
  `cpu_executor().submit(...).result()` 二重ホップも解消）。
- **watch_roots**: `tests/test_phase6_watcher.py` **12 件** —
  `/proc/self/mountinfo` 解析（最長一致・8 進エスケープ・network fstype 集合・
  network 木の中の local bind は local 判定）、path→type 最長一致、
  root 選別（欠損 / network / 重複）、**既定 OFF**（`MM_WATCH_ROOTS=0` で
  inotify を 1 本も arm しない）、**実 inotify 端到端**（外部プロセスが
  ファイルを 1 個作ると `models_changed {type:"checkpoints", reason:"fs-watch"}`
  が ws へ流れる = Phase 5 リスナーを無改修で再利用できることの証明）、
  **degrade**（`MaxFilesWatch` → セッション解放 + 600 s クールオフ + TTL へ、
  クールオフ中は新規 arm しない）、`need_rescan` → `{type: null}` の全面無効化、
  type 単位クールダウン（バルクコピーで 1 回のブロードキャストに畳む）。
  Rust L1 4 件（実 inotify イベントでの start/poll/stop 往復・欠損 root の
  スキップ報告・drain/dedupe・diagnostics）。
- **バイナリサイズ**（`watch` feature は default-on = 同梱バイナリが `watch_*`
  を持つ。OFF なのは実行時設定の方）: linux‑x86_64 host release
  **3,137,312 B = 予算 4 MB の 75 %**（Phase 5 の 2,869,968 B から **+267 KB** =
  notify 8.2.0 + notify-debouncer-full 0.7.0 + tensor tree）。
  4 プラットフォーム合計の目安は ≈14 MB ≤ 20 MB（R6）。
