# ビュー更新パフォーマンス精査レポート（修正なし・報告のみ）

対象: ComfyUI-Model-Manager-Neo の「モデル一覧ビューの更新」全般
（`GET /model-manager/models/{type}` のサーバー側スキャン → JSON → フロントの
ストア更新 → グリッド再計算 → 描画）

依頼内容に従い、**コード修正は行っていません**。以下は精査で特定した改善候補の
報告です（影響度の大きい順）。箇条の `(file:line)` は 2026-09-14 時点のものです。

---

## A. サーバー側スキャン（最大のコストはここ）

### A-1. 更新のたびに全タイプ・全ファイルを毎回歩き直す（キャッシュ無し）★影響: 大

`py/manager.py:scan_models` は呼ばれるたびにモデルルート全体を再帰 walk し、
全エントリの stat / サイドカー確認を行う。差分検知・mtime キャッシュ・ETag が
一切ないため、「1 ファイル増えただけ」でも数万ファイルの walk が毎回走る。

- 改善案 1: タイプ単位のスナップショットキャッシュ（結果 + 走査対象ディレクトリの
  `(path, mtime_ns, size)` 一覧）を持ち、ディレクトリ構成の mtime が不変なら
  キャッシュを返す（ファイル内容の変更は stat に現れるので mtime 比較で検出可能）。
- 改善案 2: レスポンスに ETag を付与し、フロントは `If-None-Match` で 304 を受け
  る（JSON 転送・パースも不要になる）。
- 改善案 3: `watchdog` 等で文件系统イベントを購読し、変更のあったサブツリーだけ
  再走査する（導入コストは高め）。

### A-2. 1 回のリフレッシュで全タイプを並列フルスキャン ★影響: 大

`src/hooks/model.ts:refreshAllModels` は `folders` の全キー（= ComfyUI が知る
全モデルタイプ）へ同時に `/models/{type}` を撃つ。タイプ数 × A-1 のコストが
毎回かかるうえ、ディスク I/O が競合して個々のスキャンも遅くなる。

- 改善案: 「現在表示中のタイプ + 星/選択中など参照中のタイプ」だけ即時スキャン、
  残りは A-1 のキャッシュ前提でバックグラウンド間引き更新にする。

### A-3. 同一タイプの重複スキャンが重なる（サーバー側 single-flight 無し）★影響: 中〜大

更新トリガーは多い（マネージャ開時の revalidate、ZipNN タスク完了イベント
（キューのフォルダごとに 1 回）、ダウンロード完了、手動更新、フォルダ作成/削除…）。
フロント側は世代カウンタで古い応答を棄てるようになったが、**サーバー側の walk は
重複して実行されてしまう**（数 GB ライブラリでは 1 回数秒〜数十秒）。

- 改善案: `py/manager.py` 側にタイプ単位の実行中 Promise を共有する single-flight
  （同時リクエストは同一 walk に合流）+ 完成後 N 秒のキャッシュを追加する。

### A-4. エントリごとに余分な `os.path.exists()`（= 追加 stat）★影響: 中

`py/manager.py:get_file_info` の `if not os.path.exists(entry.path)` は
`entry.is_file()` / `entry.stat()` と同情報の stat を全エントリでもう 1 回発行する。
walk が NFS 等の遅い文件系统上だとwalk時間が実質 2 倍になる。

- 改善案: 該ガードを削除（DirEntry の情報は scandir 由来で十分）。

### A-5. モデルごとに `.md` サイドカーを open+4KB 読み取り ★影響: 中

`py/manager.py:_model_page_of` は `modelPage` URL のためだけに、プレビューノートを
持つ全モデルでファイルを open し先頭 4KB を読む（スキャンごとに毎回）。

- 改善案: `(path, mtime_ns)` キーの小さなプロセス内キャッシュ、または `modelPage`
  をモデル詳細を開いたときだけ読む（グリッドの「ページを開く」はキャッシュ命中時
  のみ即時、程度に遅延解決する）。

### A-6. バッチごとに `ThreadPoolExecutor` を生成/破棄 ★影響: 小〜中

`py/manager.py:scan_models` の `BATCH_SIZE = 200` ループがバッチごとに executor を
作る（スレッド生成 overhead）。また再帰 walk 本体 (`get_all_files_entry`) は
シングルスレッドで全 DirEntry をリストに積む（メモリ圧迫 + walk 部分が並列化
されない）。

- 改善案: モジュール寿命の executor を再利用 / `max_workers` を I/O 寄りに増やす /
  トップレベルサブディレクトリ単位で walk を分割して並列化。

### A-7. JSON ペイロードが毎回フル ★影響: 小

全モデルの全フィールド（プレビュー URL 配列含む）を毎回シリアライズ・転送・パース。
A-1/A-2 が解決すればほぼ気にならなくなるが、gzip（aiohttp 側 `Content-Encoding`）
やフィールド間引きも有効。

## B. フロントエンドの更新パイプライン

### B-1. フラットビュー `list` computed が「全モデル」を毎回 flat+filter+sort ★影響: 中

`src/components/DialogManager.vue:231` — `Object.values(data).flat()` → filter →
sort → chunk。特にとりわけ重いのはソート比較関数内で **比較ごとに**
`genModelKey(model)`（文字列生成）と `isModelStarred(...)`（settings 参照）を
呼ぶ点（O(n log n) 回の文字列生成＋参照）。

- 改善案: `data` 変更時に 1 度だけ「星フラグ・小文字 haystack・ソートキー」を
  デコレーションした配列を作り（Map で缓存）、filter/sort はそれを参照する。
  検索トークンの正規表現もモデルごとでなく 1 回だけ構築する（現在は filter 内 で
  モデル×トークン回 `re.test`、regex 自体はトークン毎 1 回だが haystack 生成が熱い）。

### B-2. フォルダビューの_tree 再構築が `cloneDeep` 二重 ★影響: 中

`src/hooks/explorer.ts:dataTreeList` がタイプ一覧を **cloneDeep** して木を組み、
さらに `src/hooks/model.ts:useModelFolder.pathOptions`（編集ダイアログのフォルダ
Tree 用）も別に **cloneDeep** する。数千モデルの deep clone が更新のたびに 2 系統。

- 改善案: 木ノードは読み取り専用なので clone せず共有（children 配列だけ新規）、
  あるいは 2 系統を 1 つの tree ビルダーへ統合してキャッシュする。

### B-3. フォアグラウンド更新のローディングオーバーレイ ★影響: 体感大

`PanelLoading` はウィンドウ全体を blur するため、更新中ずっと「固まった」ように
見える。本件の修正で「マネージャ開時」は SWR（キャッシュ即時表示＋背景再検証）に
したが、**手動更新ボタンと初回ロードはまだフォアグラウンド**。

- 改善案: 手動更新も背景化し、完了トースト（既存の `refreshedModels`）で完了を
  知らせる。グリッドはアトミックに入れ替わるため中間状態は見えない。

### B-4. 更新トリガーとスキャン範囲の対応（現状マトリクス）

| トリガー                                                                    | 範囲                       | 背景?             |
| --------------------------------------------------------------------------- | -------------------------- | ----------------- |
| マネージャ初回オープン                                                      | 全タイプ                   | ✕（オーバーレイ） |
| マネージャ再オープン (revalidate, TTL 30s)                                  | 全タイプ                   | ○                 |
| 手動更新ボタン                                                              | 全タイプ + folders         | ✕                 |
| ZipNN タスク完了（キューのフォルダ毎）                                      | 1 タイプ                   | ✕                 |
| ダウンロード/アップロード完了                                               | 1 タイプ（本修正で標的化） | ✕                 |
| フォルダ作成/削除/編集保存                                                  | 1 タイプ                   | ✕                 |
| A-1〜A-3 はこの表の「全タイプ」行が走るたびに重複コストを払う、という構造。 |

### B-5. 既に良好な点（変更不要）

- グリッドは `ResponseScroll` による仮想スクロール（描画はウィンドウ分のみ）。
- プレビュー画像は `ETag` + `Cache-Control` 付き配信（304 で再送なし）。
- SVG アセットは mtime キーキャッシュ + 長期 Cache-Control。
- 検索入力はデバウンス済み。更新応答は世代カウンタで古いものを棄却（本修正）。

## C. 優先順位まとめ（提案）

1. **A-1 + A-3**（サーバー側キャッシュ + single-flight）— 体感への寄与が最大。
   これだけで「更新が遅い」の大半（重複フル walk）が消える見込み。
2. **A-2 + B-3**（スキャン範囲の限定と背景化）— 体感の「固まり」を解消。
3. **B-1 + B-2**（cloneDeep 排除とソート用デコレーション）— 大ライブラリでの
   更新後のもたつき（メインスレッドの再計算）を解消。
4. **A-4 + A-5 + A-6**（stat/IO の細かい無駄）— walk 自体の定数倍を改善。

いずれも機能変更を伴わない範囲で実装可能ですが、本依頼の通り**今回は修正して
いません**。着手する場合は A-1 → A-3 の順を推奨します。
